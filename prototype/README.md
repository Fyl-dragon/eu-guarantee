## 原型在验证什么

不是"看界面长什么样"，而是**验证四个交互命题能否成立**：

| # | 命题 | 在哪看 |
| --- | --- | --- |
| 1 | **排除即全链路排除（N-1）**：被排除商品在批量选择器里**根本不出现** | GARAN 标签 → *批量贴标* → 提示「5 个商品无法选择」，礼品卡/数字/B2B/仅部分部件全部不在列表 |
| 2 | **一份数据两处交付（N-2）**：声明与标签同源 | 商业保证声明页 → *共享数据* 区块 + 买家侧预览取自同一记录 |
| 3 | **批量原子性**：任一不合法 → 整批拒绝，无部分成功 | 批量弹窗填年份 `2` 后点「应用」→「未保存任何内容」+ 逐条原因 |
| 4 | **导出前一致性校验（B0-6）**：矛盾时阻止导出 | 审计 → *模拟一处矛盾* → 立即检出「已排除却贴有标签」，导出被阻止 |

## 怎么用（演示脚本）

**A. 看 N-1（最重要的差异）**

1. GARAN 标签 → 顶部提示「4 个已排除商品在此列表中隐藏」
2. 点 *批量贴标* → 选择器只有 **12** 个商品
3. 确认 **礼品卡 / 数字下载：路线手册 / 批发托盘 / 备用零件包 / 仅表框 都不在里面**
4. 对比：9 家竞品里有 7 家可验证的，都把礼品卡列进了选择器

**B. 看批量原子性**

1. 批量弹窗里勾一个商品
2. 年份填 `2`（法规要求 > 2）→ 点「应用到 N 个商品」
3. 看到「未保存任何内容」，且逐条列出原因

**C. 看年份格式**

1. 单个商品点 *编辑*
2. 年份输入 `2.5` 或 `2,5` → 都接受，预览渲染为 `2,5`
3. 输入 `2.1` / `4,1` / `3.0` / `2` → 全部拒绝

**D. 看一致性校验**

1. 审计 → 初始「全部一致」
2. 点 *模拟一处矛盾*（模拟竞品那类 bug：被排除商品却有标签）
3. 立即检出「已排除却贴有标签」，导出被阻止

**E. 看付费墙**

1. 侧栏「套餐」切到 `Free（演示）` → 商业保证声明显示 7 天试用入口
2. 切到 `Growth $4.99` → C1–C5 全部解锁

## 目录

```
src/
├── domain/garan.js     ★ 唯一真相：排除判定 / 五状态推导 / 校验 / 一致性
├── mock/               店铺、17 个商品、排除规则
├── components/         GARAN 预览（官方几何 + 明示非官方）
└── pages/              七个页面
public/assets/
├── notice/             24 个官方 SVG（24 语言，仅彩色）
└── garan/              3 个官方 GARAN SVG
tests/                  Playwright 验证脚本（77 项，断言为中文）
```

**`domain/garan.js` 是核心**：`checkExcluded` / `validateGaran` / `deriveGaranState` /
`selectableProducts` / `validateSnapshotConsistency` 五个纯函数，不依赖 React，
**可直接搬到服务端复用**。表单输入 `years` 会归一化为持久化字段 `yearsHalfUnits`
（`3` → 6、`2,5` → 5），展示时再格式化为 `3` / `2,5`。
所有页面都只调这几个函数，不允许第二套 if。

## 自动化验证

先在一个终端运行 `npm run dev`，再在另一个终端执行：

```bash
npm test                    # 33 + 11 + 14 + 35 = 93 项断言
node tests/verify-flows.mjs    # 纯函数边界 + 核心交互（33 项）
node tests/verify-fixes.mjs    # 审计发现问题的修复回归（11 项）
node tests/verify-audit.mjs    # 快照、历史 Tab、一致性与导出阻止（14 项）
node tests/verify-enhancements.mjs # 会员、统计 Tab、开关、搜索与排序（35 项）
node tests/screenshots.mjs     # 重新生成 screenshots/ 下 15 张关键状态截图
```

需要本机 Chrome。开发服务只监听 `127.0.0.1:5180`，端口被占用时会直接报错；
不要把旧进程当作当前源码。可用 `npm run dev -- --port 5181` 启动独立实例，
再以 `PROTOTYPE_URL=http://127.0.0.1:5181/ npm test` 指定测试目标。

**2026-10-25 本轮结果：构建通过，93/93 断言通过，0 页面运行时错误。**
截图脚本单独检查控制台错误；临时截图可用 `SCREENSHOT_DIR=/tmp` 指定输出目录。
这些结果仅证明 mock 原型行为，不代表生产 Shopify 集成或 QA-PLAN 已完成。

核对结论见 `../docs/AUDIT-PROTOTYPE.md`：v1 曾有 7 处与功能清单/PRD 不一致，
其中 3 处是会制造错误状态的实质缺陷，已全部修复。

## 已知限制

| # | 限制 | 说明 |
| --- | --- | --- |
| 1 | **GARAN 预览是近似图，不是官方渲染** | `21-asset-verification.md` §2.3 推翻了"3 个 text = 3 个字段"；brand/model 真实填写位置至今未确认。界面已明确标注 |
| 2 | 无 Onboarding 三步向导 | 原型默认"已安装已激活"，向导另做一轮 |
| 3 | 无真实店面渲染 | notice 用 `<img>` 加载官方 SVG，非真实 Liquid 输出 |
| 4 | 刷新即重置 | mock 数据在内存，无持久化 |
| 5 | 付费墙仅 UI 拦截 | 生产必须在服务端校验（`SECURITY-PCD.md` §6） |
| 5b | 「打开主题编辑器」是空按钮 | 原型无主题环境，点击只弹提示 |
| 5c | 状态机有**五个**状态，不是四个 | v2 补了 `NOT_ELIGIBLE`（已审但不合格），因为 UX-FLOWS §5.7 要求区分"没看"与"看了不合格" |
| 6 | 未做移动端适配 | 后台原型按桌面设计；Polaris 自身有一定响应式 |
