### 0.3 标注与展示状态

- **已有设计**：能在上述权威文档中找到直接依据，但仍待评审，不等于已批准或已实现。
- **推导**：由商家流程推导出的内部管理问题，附推导依据。
- **[设计判断]**：本文新提出的角色、页面、交互、指标口径或取舍，需评审确认。
- **[待验证]**：依赖 Shopify 平台行为、真实数据、隐私评审或后续技术验证。
- **[待确认]**：需要产品、法务/隐私或负责人决策，不应在开发时自行假设。

后台所有状态字段必须能区分：

| 状态 | 含义 | 禁止的误读 |
| --- | --- | --- |
| `已观测` | 系统通过明确机制实际观察到的结果 | 不等于商家业务事实正确 |
| `商家确认` | 商家手动声明已完成某动作 | 不等于店面已生效 |
| `系统推导` | 按已记录事实和统一规则计算的状态 | 不等于人工审核结论 |
| `数据缺失` | 所需记录尚未采集或未同步 | 不得显示成 0、失败或正常 |
| `未知` | 冲突、过期或无法判断 | 不得强行归入成功/失败 |

“管理”在本文中指观察、定位、统计、少量受控运维、App 退款工作流和商家协作，不指内部人员替商家编辑业务事实。

术语约束：本文的“订单”若无额外限定，仅指买家店铺订单，属于禁止读取范围。商家购买 App 产生的记录统一称为“应用订阅”“应用计费事件”“Charge”“Credit”或“退款申请”，不新建含混的 `Order` / `BillingOrder` 对象。`PRD.md` 中的买家索赔/售后退款与本文 App 订阅退费是不同业务。

## 1. 背景、目标与非目标

### 1.1 为什么需要内部后台

商家端围绕 notice、GARAN、Statement 的同源配置、全链路排除、版本化交付和事实留痕展开。随着店铺增多，内部团队需要回答三类问题：

1. **经营问题**：安装后有多少店铺完成配置、转为付费并持续使用？订阅、Charge、Earning、Credit 分别发生了什么？
2. **支持问题**：某家店为什么没有看到 notice、无法配置 GARAN、没有声明或出现版本不一致？商家提出的问题由谁跟进、是否已答复和解决？
3. **系统问题**：失败发生在商家配置、发布投影、声明请求、订阅/计费同步、任务执行还是 GDPR 删除？能否通过分类日志和关联 ID 还原？
4. **协作与财务问题**：商家如何提交单据、申请 App 退费、获得回复或跟踪新需求？审批、人工退款与平台核验分别进行到哪一步？

现有商家 `AuditEvent` 只解决商家维度的事实留痕，不能替代内部跨店权限、匿名交付记录、订阅/计费事实、任务执行记录、工单/附件、退款审批和内部操作审计。

### 1.2 首期目标

- 提供跨店搜索与店铺 360° 只读视图，快速定位生命周期、配置、发布和订阅状态。
- 为客服和运维提供可解释的 notice、GARAN、Statement、任务和 GDPR 排障证据。
- 提供与 `PRD.md` §7 对应的轻量经营指标，以及必要的配置/发布健康指标。
- 对安全、可重入的失败任务提供受控重试，并核对最终执行结果。
- 建立独立内部身份、最小权限、敏感访问与内部操作审计。
- 提供分类日志检索和跨模块关联，支持 App 订阅、Charge、Earning、Credit 的查询、对账和异常排障。
- 提供 App 退款申请、独立审批、Partner Dashboard 人工执行、结果复核和公开进度，不把批准或人工登记当作退款成功。
- 提供统一的双向工单/意见反馈、私有附件、需求去重与公开进度；本期不依赖主动通知完成闭环。

### 1.3 首期非目标

- 不替商家编辑商品事实、GARAN、排除规则、notice 配置或 Statement。
- 不做内部人工“合规审核”、合规通过标记、合规评分或法律背书。
- 不读取买家订单号、订单金额、买家身份或联系方式，不为报表新增买家 Order/Customer 数据；工单、日志和附件同样适用。
- 不做完整 CRM、全渠道客服中心、ERP、财务总账、法定发票、买家售后退款或大型 BI；轻量工单和 App 退费工作流不在此排除范围内。
- 不做通用 worker 控制台、任意 webhook 重放、任意 SQL/参数执行或商家身份模拟。
- 不把批量 CSV、逐变体、商家审计导出、保修登记等 P1 商家能力带入首期。
- 不提供跨店批量导出、批量修改、全局打印 token 轮换、普通客服发 credit/取消订阅/改套餐入口。
- 不承诺通过通用 API 一键现金退款；不在人工登记或平台核验前宣称已退款/已到账。
- 不提供需求交付日期保证；已规划、处理中均不等于承诺排期。
- 邮件、Webhook、催办、SLA 提醒及其他主动通知属于下一版本，本期只有站内消息、公开状态和必要查看记录。
- 不将“重试成功”“内容请求成功”“审批通过”表述为“店铺已合规”“买家已阅读/留存声明”或“退款已完成”。

产品文案继续遵循 `PRD.md` §9；本产品是展示与交付工具，不是法律意见。

## 2. 商家需求分析与后台需求映射

### 2.1 商家需求带来的内部问题

商家主要 ICP、次要 ICP 和 JTBD 以 `PRD.md` §3–§4 为准。内部后台不再划分一套商家类型，而是保留两类商家的差异：

- **仅 notice 商家**可以在不配置 GARAN/Statement 的情况下完成其核心任务；不能把后续空白误判为流失或配置失败。
- **有自有耐用性保证的商家**需要完成 GARAN 和 Statement；后台应能定位未审核、未贴标、被拒绝、未发布或交付异常。
- 商家需要证明“当时配置和展示了什么”，内部人员只能展示事实记录与一致性结果，不能追加法律判断。

## 3. 内部角色、JTBD 与权限

### 3.1 角色

以下均为 **[设计判断]**。首期采用主业务角色加显式独立权限，不建设复杂组织系统。

| 角色/权限 | JTBD | 首期定位 |
| --- | --- | --- |
| 客服/运营支持 `support` | 定位店铺/交付问题，回复工单、分派和补充资料 | 跨店业务只读 + 工单处理；无任务重试、退款审批或默认财务明细权限 |
| 技术运维 `operator` | 判断系统故障、技术升级、重试安全任务和诊断计费同步 | 跨店只读 + 白名单重试；不可修改商家事实或审批退款 |
| 财务处理 `finance` | 查询 App 计费明细、处理退款申请和外部执行/复核 | 独立主角色；具体退款能力仍需独立权限，默认无商品/声明正文权限 |
| 只读分析/管理者 `analyst` | 查看聚合指标、漏斗、工单趋势和异常 | 聚合/脱敏；默认不看店铺正文、附件或财务明细 |
| 账号管理权限 `account_admin` | 供应/停用内部账号、调整角色/权限、查询内部审计 | 独立授予；不自动获得 support/operator/finance/product_triage 能力 |

独立权限：`refund_approve`、`refund_execute`、`refund_review`、`product_triage`。退款执行人与复核人必须分离。每个账号只有一个主业务角色，可另加明确权限；不存在默认可做任何事的超级角色。

一个账号的主业务角色决定基础可见范围，独立权限只增加指定动作，不改变商家数据边界。账号供应、角色/权限变更和停用均须审计并失效旧授权上下文。身份供应方、MFA 和离职回收流程见 §10。

| 内部访问/操作审计 | 仅本人记录（可选） | 仅本人记录（可选） | 仅本人记录（可选） | 禁止 | 查看 |
| 商家商品事实、排除、notice、Statement 写入 | **全部禁止** | **全部禁止** | **全部禁止** | **全部禁止** | **全部禁止** |
| 发 credit、取消订阅、改套餐 | **全部禁止** | **全部禁止** | **默认禁止，另行评审** | **禁止** | **禁止** |
| 跨店批量导出、商家身份模拟 | **全部禁止** | **全部禁止** | **全部禁止** | **全部禁止** | **全部禁止** |

### 3.3 授权原则

- 内部后台是独立信任边界，不能复用商家 `authenticate.admin` session 作为员工身份，见 `SECURITY-PCD.md` §4。
- 内部跨店访问不等于任意访问；每次请求都需校验角色、资源、动作和显式店铺上下文。
- 商家端“查询必须带 shopId”的规则仍需保留；内部聚合/跨店查询是另一条受控路径，不得暴露给商家或买家端。
- 直接访问 URL、修改请求参数或重复提交都不能绕过授权。
- 首期没有商家授权后的“代操作”流程；如未来提出，必须单独评审范围、时限、审批和审计。

## 4. 信息架构、页面与通用要求

### 4.1 八个一级模块

| 模块 | 首期页面 | 默认使用者 | 首期取舍 |
| --- | --- | --- | --- |
| 店铺管理 | 店铺列表、店铺 360°、生命周期/订阅摘要 | support、operator | 默认入口；只放摘要和授权链接 |
| 配置与发布排障 | notice/GARAN/排除只读视图、快照/一致性、发布尝试 | support、operator | 只读事实和版本差异；无强制修复 |
| 声明交付排障 | Statement 版本、匿名交付记录与错误视图 | support、operator | 无订单/买家检索，无正文编辑 |
| 统计分析 | 轻量经营概览、漏斗、订阅留存、系统健康 | analyst；其他角色按权限 | 展示口径、更新时间与覆盖率；无自定义 BI |
| 运行记录 / 日志中心 | 分类日志、关联排障、任务/GDPR、受控重试 | support、operator、finance 按类别 | 不混放原始 payload；ADM-14–16 保留专属页 |
| 计费与退款 | App 订阅/计费事件、退款申请、审批、人工执行与复核 | finance、support 按权限 | 无买家订单、无正式会计报告、无一键现金退款承诺 |
| 商家支持 / 意见反馈 | 工单、双向回复、内部备注、需求评审、公开进度、附件 | support、finance、operator、product_triage | 统一工单；主动通知后置，不做完整 CRM |
| 内部账号与审计 | 内部账号、独立权限、内部访问/操作日志 | account_admin | 无复杂组织或通用审批平台 |

不另设“人工合规审核”“官方素材管理”“财务总账”模块。F2 的素材/语言版本在配置排障页只读呈现，F9 在店铺摘要、统计和计费与退款模块分层呈现。店铺 360° 可显示未结工单/退款摘要，但不成为第二个处理页。

### 4.2 所有页面的统一状态要求

每个 Must/Should 功能都必须按适用场景覆盖：

- Loading、Ready、Empty、No result。
- Partial data、Stale、Unknown、数据尚未同步。
- Forbidden、直接 URL 越权、跨店上下文不合法。
- 外部服务失败、超时、重复请求、并发状态变化。
- 数据更新时间和来源；无数据不能显示为 0。
- 适用时的敏感访问或操作审计结果。

空态需要说明“为什么为空”和下一步：例如尚未安装、筛选无结果、数据未接入、无权限或确实没有记录。错误详情只显示经过白名单处理的内部错误分类和关联 ID，不显示密钥、完整 payload 或堆栈。

### 4.3 通用查询与展示

- 店铺查询以规范化 shop domain 或内部 `shopId` 为入口；商品查询必须限定在已授权店铺上下文。
- 列表采用服务端分页和稳定排序；筛选条件可回看，避免跨页重复或遗漏。
- 时间戳统一保存绝对时间，界面显示时区；统计默认时区见 §7.1。
- 关联 ID 可复制；access token、完整打印 token、完整 webhook payload 永不展示。
- 长文本默认截断/脱敏；可按权限在原业务记录中查看，敏感访问留痕，但不得把完整敏感正文复制到 InternalAuditEvent。

## 5. 端到端后台流程

### 5.0 分类日志关联排障

```text
从店铺、对象、错误或 correlation ID 进入日志中心
  → 选择记录类别和时间范围
  → 查看安全摘要、来源、结果和同步时间
  → 进入原始配置/任务/计费/工单/内部审计记录
  → 无权限时只显示“存在关联但不可访问”
```

日志中心不重建原始记录的状态机，不复制工单正文、附件内容或原始 webhook。缺失、未同步、未知与无权限必须可区分。

### 5.1 客服按店铺排障

```text
收到店铺域名或内部 shopId
  → 查询店铺并核对生命周期/数据同步状态
  → 选择 notice、GARAN、Statement、订阅或 GDPR 问题类型
  → 查看当前事实、版本、最近失败和只读时间线
  → 区分商家配置问题、数据缺失、系统失败、暂不可判断
  → 给商家修复入口/说明，或带关联 ID 转运维
```

客服不代替商家修改配置；无法判断时明确说“未知”，不以手动确认或单一成功日志作结论。

### 5.2 配置与发布排障

```text
当前 DB 配置版本
  → 最近 ConfigSnapshot / StatementVersion
  → 已发布 projectionVersion 与最后成功时间
  → 发布尝试、错误分类、重试次数
  → 定位“未配置 / 未发布 / 发布过期 / 发布失败 / 数据缺失”
```

必须重读当前 DB 真相，不能把旧快照当成最新配置。只有满足 §5.4 的任务才显示重试入口。

### 5.3 声明交付排障

```text
shopId + StatementVersion / 时间 / 匿名内部关联 ID
  → 检查套餐同步、有效版本、LABELLED 商品与语言
  → 查看内容请求或打印页的匿名结果
  → 区分不适用、不渲染、认证/签名失败、超时、成功、未知
```

不支持按订单号或买家身份检索。匿名或预认证态的平台行为按 `TECH-DESIGN.md` §4.2.1 标为 `[待验证]`，不得预设一定能记录浏览器端结果。

### 5.4 受控任务重试

```text
operator 选择一条失败任务
  → 服务端重新检查当前账号/权限、任务类型、shopId、店铺生命周期和任务状态
  → 检查持久化执行上下文、幂等键、重试上限、是否已有更新尝试
  → 填写理由并二次确认
  → 原子创建一个受控尝试（不修改原任务参数）
  → 展示新关联 ID、执行状态、最终结果与内部审计
```

准入条件：

1. 任务类型经过技术评审列入白名单，且有持久化、最小化后的内部执行上下文、幂等键和明确结果；不得以原始 webhook 请求或任意编辑参数作为重试输入。
2. 当前状态仍允许重试；已执行中、已成功、已过期、已去标识、凭据/授权失效或被后续版本/事实取代的任务不得重试。已卸载店铺不得重试依赖 Shopify 凭据的投影发布。
3. 达到任务类型配置的上限后禁止继续；页面必须显示已用次数和原因。
4. **[设计判断]** 请求幂等以原任务、租户、操作者和本次操作请求键为作用域，由服务端原子去重；同一请求在双击、刷新、重登或网络重放后返回原关联 ID，不重复创建。每次获准的新重试都占用该任务上限，不能把“一次”误解为永久只允许重试一次。
5. 执行尝试必须有在途租约、超时和孤儿恢复规则；执行结果未知、审计成功但响应丢失、执行成功但响应丢失时先核对事实，不盲目再试。租约/超时值和孤儿任务能否续跑为 **[待验证]**。
6. `shop/redact` 与 `app/uninstalled` 分别定义可重入条件；重复接收或受控重试不得重复产生业务结果，任务已删除完成或店铺事实已变化时禁止继续。

禁止重试/重放：商家配置写入、Statement 发布、套餐变更、无幂等保障的任务、任意原始 webhook 参数。Statement 买家浏览器重试不等于后台可重放任务，首期仅只读排障。

### 5.5 统计分析与下钻

```text
选择时间范围/指标
  → 查看定义、分子分母、来源、更新时间与覆盖率
  → 区分业务变化、同步延迟和数据缺失
  → analyst 查看聚合趋势
  → 有店铺级权限的 support/operator 才下钻到店铺列表
```

### 5.6 卸载与 GDPR 核对

```text
webhook 接收记录
  → 验证/去重结果
  → 实际执行任务
  → 完成、失败或部分完成
  → 必要时进入受控重试
  → 最小执行回执与内部审计
```

HTTP 200 只代表接收响应，不代表删除完成。`shop/redact` 后不得继续展示已删除的商家配置；也不能手动把任务标成“已删除”。

### 5.7 内部账号与审计

```text
授权负责人供应账号/授予角色
  → 独立身份源完成认证
  → 按最小权限使用后台
  → 角色变更、敏感访问和受控操作留痕
  → 角色变更/权限移除/停用使旧授权上下文失效；执行动作前再校验
  → 停用/离职回收后会话失效且不可再访问
```

角色变更、权限移除和账号停用都必须使旧授权上下文失效。每个页面、API 和重试执行前重新校验当前账号状态与权限版本；页面打开后降权再提交必须拒绝。已启动任务的继续/取消策略、审计归属与结果展示需在技术设计中明确，不得因操作者降权而删除既有审计。

具体身份供应、会话最长时效、权限变更生效时限和紧急访问流程是开发前置决策，见 §10。

### 5.8 App 计费查询与对账

```text
店铺/平台引用/时间范围
  → 查看本地功能 plan 与 Shopify 当前订阅
  → 分类查看订阅历史、Charge、Earning、Credit
  → 核对同步游标、回补范围、延迟和冲突
  → 给出已核实事实或“实际支付状态未知”
```

`ACTIVE` 不代表已收款，Charge 表示商家被计费，Earning 是 Partner 收益事实，Credit 是费用抵扣。Partner API 数据只作运营分析，不作为正式会计/财务报告。当前订阅与历史事件的官方来源见 `TECH-DESIGN.md` §9。

### 5.9 App 退款申请、审批、人工执行与复核

```text
商家提交 App 退款申请与凭证
  → support 核对 charge/补件并沟通
  → 独立 refund_approve 审批（申请人不可自批）
  → refund_execute 到 Partner Dashboard 人工办理
  → 登记执行人、金额、币种、时间与平台引用
  → 另一授权人员复核，或可靠平台证据核验
  → 已核实部分/全额、失败或未知
  → 更新关联工单的公开状态/回复
```

批准、人工登记、平台核验和商家实际到账是不同事实。未支付费用进入 App credit 评估分支；取消订阅不等于退款。平台限制或证据不足时保持待处理/未知，不强行关闭为成功。具体官方限制见 ADM-22 和 `TECH-DESIGN.md` §9。

### 5.10 工单与意见反馈闭环

```text
商家选择 QUESTION / ISSUE / BILLING / REFUND / FEATURE_REQUEST
  → 填写主题/描述，按权限上传私有附件
  → support 分派、公开回复或请求补充
  → 必要时关联排障记录、退款申请或产品需求
  → 标记 RESOLVED，商家可确认或 REOPENED
  → 最后 CLOSED；状态变化保留历史
```

内部备注与公开回复使用不同动作和字段。FEATURE_REQUEST 可增加去重、内部评审、主需求关联和公开进度；合并不暴露其他商家的店铺或内容，`PLANNED` 不承诺日期，`RELEASED` 需要真实发布里程碑。邮件、Webhook、催办与 SLA 提醒不在本期，闭环仅依赖站内公开消息和状态。

## 6. 功能清单与验收标准

### 6.1 优先级与通用验收

优先级使用 MoSCoW：

- **Must / 首期**：没有它就无法安全提供跨店管理、排障或基本统计。
- **Should / 首期（有门槛）**：有价值，但必须等底层记录和安全条件满足才开放。
- **Could / 后续**：不阻塞首期，可在真实使用后追加。
- **Won’t / 首期**：见 §1.3，不得以隐含需求方式进入开发。

通用验收 `ADM-G` 适用于下面每项功能：

- **ADM-G1 权限**：页面、直接 URL、API 和导出/重试动作均按 §3.2 授权；隐藏按钮不算权限控制。
- **ADM-G2 数据诚实**：每项数据有来源、更新时间和状态；缺失/过期/未知不显示为 0、成功或失败。
- **ADM-G3 状态覆盖**：正常、空、无结果、部分数据、无权限、失败、超时和重复请求有明确界面与后续动作。
- **ADM-G4 隐私**：请求、日志、页面和审计均不出现买家/订单标识、access token、完整打印 token 或完整 webhook payload。
- **ADM-G5 审计**：敏感详情访问、角色/权限变更、受控操作、公开回复、退款审批/执行/复核、附件上传/下载/删除记录操作者、动作、对象、理由（适用时）、时间、结果和关联 ID；审计不复制完整正文。
- **ADM-G6 只读边界**：任何内部角色都不能从这些页面写入商家的商品事实、GARAN、排除、notice 或 Statement。工单、退款、需求评审和附件的受控写不改变这一边界。
- **ADM-G7 对外事实**：批准、执行人登记、平台核验、商家实际到账、公开回复、已查看、已解决分别为不同事实，任何一项不得冒充另一项。

### 6.2 店铺管理

#### ADM-01 店铺搜索与列表 — Must / 首期

- **角色/追溯**：support、operator；关联全部 F1–F9。
- **页面与数据**：按域名/内部 ID 精确查询；按安装、Onboarding、套餐、配置进度、发布异常、卸载状态筛选。展示域名、生命周期、订阅摘要、配置摘要、最近异常、数据更新时间。
- **来源**：Shop（已有设计）+ 生命周期、订阅、配置/发布聚合（需补记录）。
- **验收**：`ADM-01-A` 精确搜索只返回目标店，筛选与详情使用同一状态口径；`ADM-01-B` 无结果、未同步、分页越界和部分字段缺失有可区分状态；`ADM-01-C` analyst 不能通过列表接口获取未授权店铺级明细。
- **异常/审计**：店铺详情敏感访问按权限留痕；列表本身不记录无必要的全文内容。

#### ADM-02 店铺 360° 详情 — Must / 首期

- **角色/追溯**：support、operator；finance 仅可见必要店铺摘要；关联 F1–F9/F11。
- **页面与数据**：生命周期、Onboarding、订阅摘要、notice、GARAN/排除、Statement、快照/投影、最近异常、未结工单/退款摘要和只读时间线；提供到对应排障页的授权链接。
- **来源**：现有八类业务实体 + 生命周期/订阅/执行/工单摘要记录。
- **验收**：`ADM-02-A` 每个 F1–F9/F11 区域都有状态、来源和更新时间，无功能时说明原因；`ADM-02-B` 当前配置、最近快照和已发布版本分开显示，不合并为“正常”；`ADM-02-C` 页面没有任何商家配置编辑动作，工单/财务摘要不能绕过原页面权限。
- **异常/审计**：卸载或删除后按保留结果显示，不继续暴露已删除内容；生产者地址等敏感字段按 §3.2 处理。

#### ADM-03 生命周期与订阅时间线 — Must / 首期

- **角色/追溯**：support、operator；finance 按权限查看；关联 F9 和安装/卸载。
- **页面与数据**：首次安装、重装、卸载、试用开始/结束、套餐/账期、订阅状态、最近同步、取消/升降级时间；区分本地功能套餐与 Shopify 订阅事实；仅保留摘要并链接 ADM-20。
- **来源**：Shopify 安装/webhook、Partner `activeSubscription`/历史事件 **[待验证]**；本地 Shop 仅作对照。
- **验收**：`ADM-03-A` 本地 plan 与订阅状态不一致时显示冲突和最近同步时间，不自行判定已收款；`ADM-03-B` 重装、取消、年付和试用期不会覆盖首次安装事实；`ADM-03-C` 不提供人工改套餐、发 credit、取消订阅或发票入口，App 退款只通过 ADM-21/22 受控流程。
- **异常/审计**：同步失败产生可关联错误，不以最后一次成功记录冒充当前状态。

### 6.3 配置与发布排障

#### ADM-04 notice 与官方素材只读视图 — Must / 首期

- **角色/追溯**：support、operator；关联 F1/F2。
- **页面与数据**：四处 notice 开关、显示形态、店铺语言、素材/语言/发布版本、商家放置确认、系统观测状态（若存在）。

- **页面与数据**：店铺、App charge 引用、申请金额/原币币种、原因、说明、关联工单和凭证；申请/沟通状态与外部执行状态分开显示。
- **来源**：RefundRequest、AppBillingEvent、SupportTicket/Attachment（需补）；平台可退余额与支付事实 **[待验证]**，不凭 Charge 推断已支付。
- **状态**：申请为 `SUBMITTED / NEEDS_INFO / IN_REVIEW / APPROVED / REJECTED / CANCELLED / CLOSED`；审批为 `PENDING / APPROVED / REJECTED`；外部执行为 `NOT_READY / AWAITING_MANUAL / EXECUTION_RECORDED / VERIFIED_FULL / VERIFIED_PARTIAL / FAILED / UNKNOWN`。
- **验收**：`ADM-21-A` 无 charge、跨店 charge、金额/币种异常、重复申请、超余额、重复部分退款有明确处理；`ADM-21-B` 申请人不可自批，support/operator/account_admin 不能借 URL/API 审批；`ADM-21-C` 二次确认、版本/并发校验、幂等和理由审计有效，批准不等于退款成功；`ADM-21-D` 未支付费用进入 App credit 评估分支，取消订阅与退款不自动联动。
- **异常/审计**：审批阈值和双人规则未定前，高金额申请不得进入执行；审批不触发未经批准的 credit、取消或改套餐。
- **保留**：申请与决定按财务/隐私评审期限保存，凭证正文不复制到审计事件。

#### ADM-22 Partner Dashboard 人工执行、登记与复核 — Must / 首期

- **角色/追溯**：仅 finance 的 `refund_execute` 登记执行、`refund_review` 复核；执行人与复核人不得相同；support 查看授权进度并沟通。
- **页面与数据**：批准后进入指定 charge Details，人工 Issue refund；登记执行人、时间、金额、币种、平台引用和凭证，再由另一授权人员或可靠平台证据核对，更新关联工单。
- **来源**：RefundExecution/Review、Partner charge details（需补/待验证）；官方人工退款路径见 `TECH-DESIGN` §9.5。深链只作入口，不保存 Partner 密码或模拟员工操作。
- **验收**：`ADM-22-A` 人工登记只表示执行人声明，不能单独改为成功，证据不足保持待复核/未知；`ADM-22-B` 重复登记、金额不一致、部分退款累计、后续新退款、同步超时和响应丢失均有处理；`ADM-22-C` 超过 USD 1,000、发票超过 12 个月或 ACH 限制时指引 Shopify Support，不承诺后台完成；`ADM-22-D` 复核/平台核验与商家到账不混称，执行/复核人员不可相同。
- **异常/审计**：执行、复核、凭证查看、失败和未知均留痕；商家通过关联工单公开状态获知进度，本期不发主动邮件。
- **保留**：执行凭证与复核记录按财务依据和最小化原则设期限，卸载/redact 冲突见 §10。

### 6.9 商家支持与意见反馈

#### ADM-23 统一工单与双向沟通 — Must / 首期

- **角色/追溯**：商家处理本店工单；support 分派/回复/处理；operator 技术升级；finance 处理授权财务部分；关联 F11 和退款/排障功能。
- **页面与数据**：类型 `QUESTION / ISSUE / BILLING / REFUND / FEATURE_REQUEST`，店铺、主题、描述、分类、优先级、状态、负责人、公开回复、内部备注、关联资源和必要查看记录。
- **来源**：SupportTicket、TicketMessage、TicketResourceLink、ReadCursor（需补）；不建立买家 Order/Customer 关联。
- **状态**：`OPEN / PENDING_MERCHANT / PENDING_INTERNAL / RESOLVED / REOPENED / CLOSED`；重开保留原解决记录，SLA/自动关闭未评审前不承诺。
- **验收**：`ADM-23-A` A 店商家不能枚举或访问 B 店工单、回复、附件、charge 或日志；`ADM-23-B` 内部备注、内部优先级和员工私有字段不进入商家响应；`ADM-23-C` 公开回复与内部备注使用不同动作/字段，重开不删除历史；`ADM-23-D` 查看详情才更新该主体游标，列表加载不误标全部已读；`ADM-23-E` 无邮件/第三方通知时仍能通过公开回复和状态完成闭环。
- **异常/审计**：发送失败、并发回复、跨店关联、无权限内部备注和重开窗口有明确状态；“已查看”不代表同意、解决、收到邮件或退款成功。
- **保留**：会话、内部备注和查看记录分别评审期限；商家不可见内容不得通过导出/日志泄露。

#### ADM-24 需求去重、评审与公开进度 — Should / 首期

- **角色/追溯**：商家提交和查看本店需求；support 提交/关联；仅 `product_triage` 合并、内部评审和公开进度；关联 F11。
- **页面与数据**：FEATURE_REQUEST 复用工单、回复、附件和状态；支持重复候选、主需求关联/合并、保留原始提交、内部优先级、评审备注、负责人和真实发布里程碑。
- **来源**：SupportTicket + FeatureTriage（需补）；公开进度与内部评审字段分离。
- **验收**：`ADM-24-A` 合并不向其他商家暴露店铺或正文，原提交者仍可查看本店提交与公开进度；`ADM-24-B` 内部 triage 备注不公域返回；`ADM-24-C` 公开进度覆盖已提交、评估中、已规划、处理中、已发布、不计划/关闭，`PLANNED` 不承诺日期，`RELEASED` 必须关联真实发布证据；`ADM-24-D` support 无 product_triage 时不能公开计划/发布状态。
- **异常/审计**：循环关联、重复合并、错误公开发布、撤回公开状态需有冲突处理和审计；内部优先级不等于对商家的承诺。
- **保留**：需求及公开进度可在店铺服务期内保留；卸载/redact 按用途删除或去标识，不为统计无限保留店铺域名。

#### ADM-25 私有附件与凭证 — Must / 首期

- **角色/追溯**：商家仅本店上传/下载/撤回允许撤回的附件；support/operator/finance 按关联工单权限访问；关联 ADM-21/23/24。
- **页面与数据**：私有对象存储，数据库仅保存 attachment ID、shopId、ticket/message ID、上传主体、文件名安全处理值、声明/真实 MIME、大小、数量、校验和、扫描状态和时间；无永久公开 URL。
- **来源**：Attachment 元数据与私有对象存储（需补）；扫描服务/区域 **[待验证]**，不借道商家 Files，不新增 `write_files`。
- **状态**：`PENDING / CLEAN / INFECTED / FAILED / QUARANTINED`；未通过不可下载，失败/感染不得伪装可用。
- **验收**：`ADM-25-A` 声明 MIME、真实内容、扩展名、大小和数量校验有效，SVG/HTML/脚本等危险内容不内联；`ADM-25-B` 短时授权下载绑定店铺、附件、身份、权限和用途，跨店 IDOR/过期链接/降权后下载均拒绝；`ADM-25-C` 上传、下载、删除、扫描和失败授权均审计，普通日志不记录签名 URL、文件内容或敏感文件名；`ADM-25-D` 删除覆盖对象、扫描副本、缓存与元数据。
- **异常/审计**：明示不得上传买家订单/身份、支付资料或完整 token；疑似 PII 隔离/删除流程 **[待确认]**，不默认可长期保存。
- **保留**：附件期限独立于会话并纳入备份/缓存/日志删除；第三方处理方更新 `SECURITY-PCD` 数据清单。

### 6.10 后续候选，不进入首期承诺

- **Could / 后续**：保存筛选器、订阅异常通知、轻量趋势对比、经审批的店铺级单次导出。
- **下一版本通知**：邮件、Webhook、催办、SLA 提醒和其他主动通知；不影响本期站内工单与状态闭环。

## 7. 指标、事件与数据可用性

### 7.1 统一统计约定

以下口径为 **[设计判断]**，需在数据评审中确认；目标值来自 `PRD.md` §7，不代表当前结果。

- 默认使用 UTC 计算日/cohort，界面可切换显示时区；跨时区报表必须注明口径。
- 店铺去重键使用内部 `shopId`，不用域名文本重复计数；域名变化映射方式 `[待验证]`。
- 测试/内部店铺默认排除，并披露排除规则和数量。
- 每项指标显示来源、最近成功同步时间、数据延迟、覆盖率和可计算状态。
- 数据迟到可重算，保留指标版本/重算时间；不能静默修改历史而不留说明。
- 刷新频率首期可为异步准实时或定时聚合，具体目标见 §10；页面不得假装实时。

### 7.2 经营指标字典

| 指标 | 定义/公式 | 数据来源 | 当前可计算性 |
| --- | --- | --- | --- |
| 当前付费商家数（北极星） | 测量时点具有有效 Growth/Pro 付费订阅、已过试用且非赠予的去重店铺数；试用不计入 | Shopify Billing 同步 + 试用事实 | **需补订阅同步**；不能只看 Shop.plan |
| 安装店铺数 | 窗口内首次成功安装的去重店铺数；重装另列，不重复算新店铺 | 安装生命周期事件 | **需补安装事实**；Shop.createdAt 不足以区分重装 |
| 安装→首次配置完成率 | 同一首装 cohort 中，在首装后 W 天内完成首配的店铺数 / 首装已满 W 天观察期的该 cohort 店铺数；起算点为首次安装完成时间 | 安装 + Onboarding + notice 配置 + 投影事件 | **需补事件；W 待产品评审**；未确定 W 前不输出正式转化率 |

| 首配观察窗口 W 与重装规则 | W 是从首装起算的连续自然日窗口；未满 W 天的样本不进入分母，超过 W 天才首配不算分子；重装不重置首装 cohort 或既有首配事实，可另建“重装后恢复配置”指标 | 生命周期/里程碑事实 | **[待确认]** W 的具体天数；PRD 的 90 天目标期不自动等于 W |

| 30 天 Free→Paid 转化率 | 首装时为 Free 的 cohort 中，首装后 30 天内首次成为付费的店铺数 / 已有完整 30 天观察的该 cohort 店铺数 | 安装 + 订阅同步 | **需补**；PRD 的 ≥5% 目标与所选 cohort 窗口需在评审对齐 |
| 付费→30 天留存率 | 首次付费满 30 天的 cohort 中，第 30 天仍为有效付费的去重店铺数 / 该 cohort 首次付费店铺数 | 订阅、取消、卸载、重装/复订事实 | **需补**；卸载/取消不计留存，未知单列 |
| MRR | 有效付费月付金额 + 有效年付金额/12 的月度归一化合计；排除试用/赠予 | Shopify Billing 订阅金额与账期 | **需补**；是合同金额指标，不是到账现金 |
| App Store 评论数/均分 | 指定时间点 App Store 外部展示的评论数与均分 | 外部页面/经批准的人工记录 | **外部数据**；首期无自动同步承诺 |

补充规则：

1. 年付 MRR 按合同金额除以 12，不扣除税费、退款、拒付或平台费用；如要展示净收入，需另立财务指标，不复用 MRR。
2. 当前定价为 USD；若真实订阅存在其他币种，汇率和折算时点 **[待验证]**，不得直接相加。
3. 付费商家、MRR 与留存均以订阅同步事实为准；本地 plan 是功能门禁快照，不能单独证明付费或收款。
4. 30 天留存的分母只含已满观察期的店铺；同步状态未知不得默认算留存或流失，应披露样本排除/缺失。
5. PRD 的 90 天目标用于对照，不改变上述 cohort 定义；若负责人选择其他窗口，必须版本化指标口径。

## 8. 权限、隐私与非功能需求

### 8.1 安全边界

- 独立员工入口、身份和认证受众；可复用部署或数据库的方案由后续技术设计决定，但权限上下文不能混用。
- 服务端逐请求鉴权；商家、买家、公开打印和内部接口使用不同授权策略。
- 内部接口不得被商家 session、Customer Account token 或打印 token 调用。
- 后台不新增 Shopify scope，继续遵循 `write_products` 边界；运营需要不是读取订单、买家、主题或商家员工数据的理由。
- 无商家身份模拟；无默认全权超级管理员；高风险能力按独立权限开放。
- 任务重试、退款审批/执行/复核、公开回复、附件上传/下载/删除采用失败关闭：权限、幂等、状态或审计任一不满足即不执行。
- Partner token 是 Partner 组织级凭据，只在服务端保管并支持轮换，不下发浏览器，不与 Shop Admin token、商家 session 混用；权限可用性见 §10。
- 退款审批、执行和复核分别授权且人员分离；support/operator/account_admin 不因角色获得默认财务能力。
- 商家只能访问本店公开工单、退款状态和附件；内部备注、内部 triage、员工私有字段和跨店日志不进入商家响应。

### 8.2 数据最小化与展示

- 不存/不查买家姓名、邮箱、电话、地址、订单号、订单金额、订单状态或 customer ID，见 `SECURITY-PCD.md` §3。
- sole trader 的生产者地址可能是自然人住所，不能笼统视为无个人数据；默认脱敏并记录敏感访问。
- 内部分析不保存 IP、User-Agent 或完整 URL token；如基础设施短期安全日志必须处理这些信息，需另列保留和访问规则。
- 内部员工账号、商家联系人、工单自由文本、退款凭证和附件可能包含个人信息，与“买家零 PII”分别建立数据清单、用途、保留、删除和访问权限，不得假装没有任何个人信息。
- 附件上传前提示遮蔽买家、支付和认证信息；疑似买家 PII 的隔离、删除和商家提示流程需隐私评审，不能因用户主动上传就默认可保存。
- 删除后的店铺回执不得默认长期保留 shop domain；去标识不等于简单删除页面上的域名，需评审日志、备份和关联记录。
- 默认不引入第三方分析 SDK 或错误追踪 SaaS；附件存储、恶意扫描及后续通知若引入新的处理方，必须更新 `SECURITY-PCD` 数据传输、隐私政策、脱敏和保留设计。

### 8.3 审计与保留

- 商家 `AuditEvent` 和内部 `InternalAuditEvent` 分离；前者回答商家配置事实，后者回答员工访问和操作。
- 内部审计不能自动继承商家 AuditEvent 的 24 个月或 RejectedAttempt 的 90 天；需按员工管理、安全调查和最小化原则另定保留期。
- 审计记录只保存必要前后差异；角色变更可记录前后角色，敏感声明正文不复制完整快照到内部审计。
- 受控操作的审计写入失败时不得继续执行；审计查询、导出（未来）和删除也需独立授权。

### 8.4 可用性、性能与可访问性

- 店铺列表、任务和审计均采用分页/有界查询；大店铺详情不能一次加载全部商品或事件。
- 统计可使用异步聚合，但必须显示新鲜度；统计延迟不能阻塞单店排障。
- 外部 Shopify 数据不可用时可展示最近已知状态，但必须标 Stale 和最后同步时间。
- 受控写需防重复提交、处理并发状态变化，并给出可追踪的最终结果。
- 页面支持键盘操作、清晰焦点、非颜色单一状态表达、可读的表格/空错态；具体 UI 语言和可访问性验收在后续 UX 设计中补充。
- 具体列表响应、统计刷新和会话时效目标见 §10，未评审前不写进对外承诺。

## 9. 需求验收与评审清单

### 9.1 产品评审

- [ ] F1–F9/F11 均有管理对象、功能和排障/统计问题，不遗漏纯 notice 商家路径。

- [ ] §5 的十一条流程能从店铺/任务/申请/工单定位到下一步，不只展示原始字段。
- [ ] 发布失败、配置不一致、声明不渲染、订阅/计费未同步和 GDPR 未完成有不同状态。
- [ ] 重试只针对白名单任务，有理由、二次确认、幂等、上限、最终结果和审计。
- [ ] 退款申请、审批、人工执行、独立复核、公开状态完整；批准/登记不等于退款成功，执行人与复核人分离。
- [ ] 工单支持公开回复与内部备注、补件、解决/重开；需求可去重与公开进度，不默认承诺排期。

### 9.3 安全/隐私评审

- [ ] 页面、URL、接口、任务、审批、执行、复核和附件下载均遵守权限矩阵；无商家 session 复用或默认跨店全权。
- [ ] 没有买家订单/身份、完整 token、完整 webhook payload、Partner token 或不必要的敏感正文扩散；工单附件不绕过 PII 边界。
- [ ] 员工身份、商家联系人、财务、工单/附件、内部审计、匿名交付和删除回执均有数据清单与保留决策。
- [ ] 内部备注/内部 triage 不进入商家响应；退款权限独立、人员分离；Partner token 只在服务端保管。
- [ ] 无人工合规审核、合规评分、法律有效等越界表述。

### 9.4 数据评审

- [ ] 每项指标有公式、分子/分母、去重、cohort/窗口、来源、时区、刷新、缺失与重算规则。
- [ ] 首配、商家确认、真实观测、内容请求成功、实际渲染、打印页成功响应和 PDF 保存不混用。
- [ ] 本地 plan 不冒充付费/收款；缺失/过期数据不显示为 0、成功或流失。
- [ ] 指标可重算，事件有 schema 版本和关联 ID，匿名事件不引入买家标识。
